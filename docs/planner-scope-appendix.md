# 선택 부록: 범위와 상세 동작

본편의 조건부 판단을 화면과 접수 흐름으로 더 구체화할 때 읽는 자료입니다. 아래 작성 예를 실제 구현이나 시험 결과로 기록하지 않습니다.

## 범위를 고르는 기준

제가 홈화면에서 남기고 뺀 것

제가 AI 서비스 홈화면을 기획할 때는 빈 대화창에서 무엇을 시작해야 할지 모르는 상황, 실제로 쓸 결과물, 이전 작업을 이어갈 방법을 함께 봤습니다. 결과물 생성, 자료 수집, 프로젝트 시작으로 입구를 나누고 헤더와 숏컷부터 재구성하기로 했어요. 범용 대화는 당시 제품의 차별 가치와 사용 이유가 약하다고 봐서 제외했고, 개인화 이력과 갤러리는 후속으로 미뤘습니다. 그래서 카드 최대 수와 정렬, 클릭 뒤 동작까지 지시에 적었습니다. 이 수업의 카드 이름과 네 개라는 수는 연습용 조건입니다.

1. 끝낼 행동에서 흐름을 찾기

누가 어디서 시작해 무엇을 남기는지 적습니다. 시작 → 입력 → 행동 → 결과가 끊기면 그 단계는 남깁니다. 다른 제품에도 있는 기능이라도 신청 완료를 알려주는 결과 화면처럼 필수인 것은 남겨야 합니다.

2. 가치와 선행 조건을 따로 보기

후보마다 핵심 흐름에서 맡는 일, 이 제품을 쓸 이유, 필요한 자료나 운영 결정을 비교합니다. 차별 가치가 약하면 제외 후보, 필요하지만 과거 기록이나 운영 기준이 없다면 미룸 후보입니다. 다른 제품에 있다는 이유만으로 빼지는 않습니다.

3. 사람이 남김, 미룸, 제외 선택하기

AI는 비교까지 돕고 선택을 기다립니다. 내 답과 남김, 미룸, 제외를 직접 입력하고 고친 범위표 전체를 붙여 확정합니다. 후속 제작 요청은 이 확정본을 따르며 설명용 기본 선택으로 되돌리지 않습니다. 선택이나 확정본이 없으면 먼저 물어보게 합니다. 이어하기가 필수라면 기본 이력 조회와 복귀 동작을 개인화 추천과 나눠 판단합니다. 필요한 이력, 노출 기준, 복귀 화면이 미정이면 명시한 가상 연습값을 쓰거나 해당 동작과 다음 결정을 보류로 남깁니다. 남김에는 끊기면 안 되는 이유, 미룸에는 대신할 경로와 다시 볼 조건, 제외에는 가치 판단과 결정을 다시 열 조건을 적습니다. 예: 개인화는 작업 이력과 노출 기준이 갖춰지면 다시 검토, 범용 대화는 이 제품에서만 필요한 사용 일이 확인되면 재검토. 이 재검토 조건은 수업에서 추가하는 판단 예입니다.

4. 대신할 사람과 질문의 끝 정하기

기능을 빼면 누가 어떤 일을 맡는지 확인합니다. 결제를 미루면 현장에서 누가 확인하나요? 결과를 바꿀 빈칸만 한 번에 하나, 최대 두 번 묻습니다. 사람의 범위 선택, 대신할 담당과 경로, 미룸과 제외의 재검토 조건이 정해지면 멈춥니다. 필수 흐름이 빠졌거나 운영 규칙을 모르면 충돌을 알리고 해당 동작은 보류합니다.

5. 확정한 범위를 제작 지시로 바꾸기

실행 조건을 정한 기능만 입력, 누르는 행동, 다음 화면, 남는 결과를 실제 문장으로 씁니다. 필요한 기능이어도 조건을 몰라 보류했다면 “동작 보류”, 이유, 미정 항목과 다음 결정을 범위표와 제작지시에 함께 남깁니다. 보류 동작은 예시 값으로 채우지 않으며 필수 흐름까지 보류됐다면 아직 확정하지 못한 흐름을 표시합니다. 자료가 없을 때의 안내, 정원과 같은 한도, 실패와 재시도도 적습니다. “카드 제공” 대신 “보고서 카드 클릭 → 보고서 시작 화면”으로 옮깁니다. 중복 제출과 마지막 자리 경쟁은 정해진 프로그램 로직으로 처리하고 AI에게 즉석 판단을 맡기지 않습니다.

가져갈 문서

범위표에는 선택, 이유, 대신할 사람, 다시 볼 조건을 남깁니다. 제작지시에는 확정한 작은 흐름의 입력, 행동, 결과, 빈 상태와 한도 처리를 적습니다. 제품 전체 PRD나 코드를 쓰는 단계까지 늘리지 않습니다.

## 완성 예 A, 내가 고른 범위에 따라 달라지는 동작

# 설명용 기본 제작지시A, 새 작업 시작을 고른 경우
입력: 시작할 작업을 선택한다. 홈에서 긴 프롬프트나 과거 이력을 요구하지 않는다.
표시: 헤더는 “무엇을 만들거나 정리할까요?”로 쓴다. 보고서 만들기 → 슬라이드 만들기 → 자료 모으기 → 프로젝트 시작을 고정 순서로 최대 네 카드까지 표시한다.
행동과 다음 화면: 보고서 카드는 보고서 작업 시작, 슬라이드 카드는 슬라이드 작업 시작, 자료 모으기는 수집 작업 시작, 프로젝트 시작은 새 프로젝트 시작 화면으로 이동한다.
남는 결과: 선택한 작업 종류가 다음 화면에 전달되고 사용자가 해당 작업의 입력을 시작할 수 있다. 홈에서 최종 보고서가 완성됐다고 표시하지 않는다.
빈 상태: 이력이 없는 첫 방문에도 네 카드를 그대로 보여준다. 가짜 최근 작업이나 빈 개인화 영역을 만들지 않는다.
연결 실패: 작업 시작 화면을 열지 못하면 “작업을 시작하지 못했습니다. 다시 시도해 주세요.”를 표시하고 같은 선택으로 다시 시도할 수 있게 한다.
이번 화면에는 범용 대화, 개인화 이력, 갤러리 입구를 넣지 않는다. 운영자는 카드 이름과 연결을 확인한다.
첫 흐름: 이력 없는 첫 방문 → 보고서 만들기 선택 → 보고서 시작 화면과 작업 종류 확인 → 보고서 입력 시작. 슬라이드·자료·프로젝트도 각각 해당 화면으로 간다.

위 본문은 새 작업만 시작하는 기본 예입니다. 내 확정 범위표를 범위표A.md, 내 선택으로 받은 제작 지시를 제작지시A.md에 저장하세요. 이어하기 조건을 정했다면 이력 조회와 복귀 동작을, 보류했다면 미정 항목과 다음 결정을 두 문서에 남깁니다. 아래 실행 조건을 정한 대안 예로 내 보류 결정을 덮어쓰지 마세요.

설명용 대안 제작지시, 이어하기의 실행 조건을 가상 값으로 정한 경우
헤더와 네 시작 카드는 유지하고 그 아래 현재 사용자만 보는 최근 작업 목록을 수정 시각 내림차순으로 표시한다. 연습값 “주간 보고서, 보고서, 작성 중”을 선택하면 해당 보고서 편집 화면으로 이동하고 같은 작업과 작성 중 상태를 이어받는다. 새 보고서를 만들거나 다른 사용자의 작업을 열지 않는다.
이력 0건이면 “이어갈 작업이 없습니다. 새 작업을 시작해 보세요.”와 네 시작 카드를 보여준다. 작업을 불러오지 못하면 “작업을 불러오지 못했습니다. 다시 시도해 주세요.”와 재시도를 제공하고 이어하기 성공으로 표시하지 않는다. 개인화 추천과 갤러리는 넣지 않는다.
범위표A에는 최근 작업 조회와 이어하기를 남김으로, 개인화 추천과 갤러리를 미룸으로 기록한다. 제작지시A에는 새 작업 시작과 이전 작업 복귀를 함께 남긴다.

설명용 보류 기록, 이어하기가 필수지만 조건을 정하지 못한 경우
범위표A: 이어하기는 필요한 기능으로 유지하되 동작 보류. 이력 저장 위치와 복귀 화면이 미정이다. 다음 결정은 사용할 이력의 저장 방식을 확인하고 어떤 작업을 어느 편집 화면에서 이어갈지 정하는 일이다.
제작지시A: 이어하기 동작은 보류. 미정 정보를 임의로 채워 최근 작업 목록이나 편집 복귀를 지시하지 않는다. 조건을 정한 새 작업 시작 부분만 지시로 남긴다. 필수 이어하기까지 포함한 흐름은 아직 확정되지 않았다고 표시한다.
두 파일에 같은 보류 이유와 미정 항목, 다음 결정을 저장한다. 이력과 복귀 조건을 정한 뒤 해당 항목만 제작 지시로 구체화한다.

## 사례 B · 정원 20명 행사에서 접수 혼선 막기

교육용 입력 B: 정원 20명 행사, 결제는 현장에서 운영자가 확인한다. 공개 실습은 별칭만 쓰며 실제 접수·결제는 하지 않는다. 신청자는 별칭을 입력하고 참석 여부를 선택한 뒤 신청한다.

필수 조건: 참석에 동의한 신청만 접수한다. 접수 성공 시 “접수되었습니다. 결제는 행사 현장에서 진행합니다.”를 보여준다. 접수 완료 인원이 20명이면 신청을 마감하고 대기 접수는 하지 않는다. 중복 제출 방지와 동시 마지막 자리 처리가 필요하다.

운영자: 행사 시작 전 정원을 20명으로 설정하고 접수자 별칭·접수 상태 목록을 확인한다. 공개 화면에 전체 신청자 목록을 노출하지 않는다. 정원 변경은 운영자가 결정한다.

후보 기능: 신청, 접수 결과, 운영자 목록, 정원 설정과 초과 처리, 온라인 결제, AI 추천, 갤러리. B의 가설은 접수 결과와 정원 처리를 남기면 입력폼만 있을 때의 접수 혼선을 줄일 수 있다는 것이다.

## 현장 결제와 중복의 기준을 사람이 선택하기

AI의 질문 예 1: 온라인 결제를 미루면 누가 언제 결제를 확인하며 신청 완료와 구분하나요?

제 답: 운영자가 행사 현장에서 확인합니다. 이번 온라인 화면은 접수 완료만 표시하고 결제 완료로 보이지 않게 합니다.

AI의 질문 예 2: 별칭이 같으면 같은 사람인가요? 이 연습에서 막을 중복을 무엇으로 정할까요?

제 답: 별칭은 사람 식별 수단이 아닙니다. 수업용 추가 결정으로 같은 브라우저의 같은 행사 제출을 중복으로 정합니다. 신청 한 건을 구분하는 임의 번호(제출 식별자)를 다시 사용해, 버튼을 여러 번 눌러도 같은 접수로 처리합니다. 여러 기기나 공용 브라우저에서 실제 사람을 식별하는 정책은 별도 결정이 필요합니다.

설명용 기본 범위표 B
남김 | 별칭 신청·접수 결과·운영자 목록·정원 20명과 초과 처리 | 신청과 운영 확인이 끊기면 안 됨.
미룸 | 온라인 결제 | 현장 운영자가 확인 | 온라인 선결제가 필요하고 결제·환불 담당과 규칙이 정해지면 재검토.
제외 | AI 추천·갤러리 | 이번 접수 완료에 맡는 일 없음 | 추천이나 공유가 해결할 구체적 참가자 일이 확인되면 재검토.
대신할 일 | 운영자가 현장 결제와 정원 변경을 결정. 온라인 접수 상태와 결제 확인을 구분.

## 완성 예 B · 신청부터 마감과 운영자 확인까지

# 설명용 기본 제작지시B, 브라우저 기준을 고른 경우
1. 운영자는 권한이 있는 화면에서 정원을 20명으로 설정한다. 정원 변경은 운영자가 결정한다. 접수 0건이면 “아직 접수자가 없습니다.”를 표시한다. 공개 화면에 전체 목록을 노출하지 않는다.
2. 신청자는 별칭을 입력하고 참석에 동의한다. 별칭이 없거나 동의하지 않으면 저장하지 않고 “별칭을 입력해 주세요.” 또는 “참석 동의를 확인해 주세요.”를 표시한다.
3. 같은 브라우저·행사의 임의 제출 식별자는 재클릭과 재전송에도 재사용한다. 같은 식별자의 재요청에는 기존 접수 결과를 반환한다. 별칭이 같다는 이유만으로 같은 사람이라고 처리하지 않는다. 처리 중에는 신청 버튼을 비활성화한다.
4. 새 신청은 중복 확인과 남은 자리 확인, 저장을 하나의 원자적 처리로 묶는다. 확인과 저장 사이 다른 신청이 끼어들어 정원을 넘지 않게 한다. 동시에 마지막 자리를 요청해도 접수는 하나만 성공하며 총 20건을 넘지 않는다. AI가 접수 여부를 고르지 않는다.
5. 성공 후 별칭과 “접수되었습니다. 결제는 행사 현장에서 진행합니다.”를 표시한다. 남는 결과는 제출 식별자에 연결된 별칭과 접수 상태 한 건이다. 결제 완료 상태를 자동으로 붙이지 않는다.
6. 정원이 차면 “접수가 마감되었습니다. 대기 접수는 받지 않습니다.”를 표시하고 새 신청을 막는다. 저장 실패 시 “접수하지 못했습니다. 다시 시도해 주세요.”를 보여준다. 재시도는 같은 제출 식별자로 하며 마감·실패를 성공으로 보이지 않게 한다.
7. 운영자는 권한이 있는 목록에서 별칭과 접수 상태를 확인하고 행사 현장에서 결제를 확인한다. 권한이 없으면 목록과 정원 변경을 제공하지 않는다. 실제 운영의 인증과 사람 식별 정책은 구현 전 별도 확정한다.
첫 흐름: 별칭 ‘참가자A’ → 참석 동의 → 신청 → 같은 접수 결과 확인 → 운영자 목록에서 한 건 확인.
한도 흐름: 교육용 완료 데이터 20건 → 새 신청 → 마감 안내 → 21번째 접수가 없음. 같은 식별자 재전송은 기존 접수만 반환한다.
이 브라우저 기준은 수업의 중복 정의이며 실제 사람의 여러 기기 접수를 막는다고 약속하지 않는다.
